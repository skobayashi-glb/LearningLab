### 0.1 開発用ツールと製品版の分離（2026-09-22追記）

製品版から学習環境を切り離せることを要件とする。学習器・Python依存・実験結果・検証用環境はAssets外の `LearningLab/` に置き、ゲームRuntimeから参照しない。将来のステージExporter/数値ImporterはEditor専用とし、製品には採用済みゲームデータと必要な戦闘処理だけを残す。共通戦闘コアを製品で使う場合も、学習通信・評価・最適化をコアに持ち込まない。

独立基盤と戦闘ホストを [LearningLab](../LearningLab/README.md) に実装した。PPO、合法行動マスク、シナリオ分割、保存・再開、評価・リプレイ、外部プロセス用JSON adapterに加え、保存済みStageDefinitionとキャラデータの書き出し、Energy制約付き出撃、敵の予算内ランダム出撃、移動・戦闘・拠点占領を実行できる。

実行方法・設定例・対応範囲は [戦闘学習の手順](../LearningLab/BATTLE.md) を参照する。Editor専用サンプルは開けた地形・隘路・迂回路の3マップ。HP・攻撃力・速度・コストの味方側上書きを指定でき、敵は別スナップショットとして固定する。

実装は単一環境・固定長観測・フィードフォワード方策。カード選択を無時間の離散操作として組み立て、確定時に戦闘を進める。状態/形状の数値計算はゲームのC#ソースをリンクするが、移動・接触回避・隊列・出撃制御等は独立実装であり、Unity本体と同一の共通戦闘コアへの統合は未完了である。未対応の飛行・支援役・位置効果・ノックバック等は読み込み時に拒否する。

2026-09-23に、操作AIを固定したキャラ数値の自動探索を追加した。[数値調整の手順](../LearningLab/BALANCE.md) を参照。初期設定ではHP・攻撃力だけを変え、速度・コスト・敵数値を固定する。役割・基準コストごとの評価caseに、指標の目標帯を明示する。trainで候補を選び、validationで個別caseも悪化しないことを確認し、holdoutは最終報告にのみ使用する。PPOと同時に学習せず、離散候補集合のランダム探索として実装する。

履歴方策、並列学習、Unityへの採用値取り込みは引き続き設計案である。短い学習の成功やシミュレーション内の成績を、実製品のバランス検証完了とは扱わない。仮の役割別目標値を製品の適正値とは扱わない。

## 1. 目的と採用構成

目的は、役割・得意不得意・意図した強弱を保ちつつ、一択になる戦略や想定外の過剰な相乗効果を発見・修正すること。全キャラの勝率・採用率を均等にはしない。

| 処理 | 更新するもの | 評価基準 |
|---|---|---|
| バランス探索 | HP・攻撃力・コスト等のゲームデータ | 役割別期待範囲、回帰検査、変更量 |
| プレイAIのRL | 方策・価値ネットワークの重み | 勝利、メイン拠点の保全 |

RLはゲームデータを直接更新しない。バランス探索中は評価方策を固定し、学習中はゲームデータを固定する。

```text
版付きキャラ・技・状態・ステージ・ルールデータ
                      ↓
             Unity非依存のC#戦闘コア
                ↙                 ↘
       Unityアダプタ              評価用CLI
   表示・音・プレイヤー入力      固定戦術 / PythonのRL
                                   ↓
                           指標・リプレイ・調整候補
```

ゲームと学習が同じ戦闘コアを使う。独立した簡易シミュレータだけで最終バランスを決定しない。

| 戦闘 | リアルタイム、固定ステップ |

## 3. Unity非依存化

### 3.1 現状と移行

命中・接敵・押し合いは `AttackShape`、`EngagementRange`、`CombatLocomotion` 等の自前計算。主要戦闘判定をRigidbodyへ委ねる構造ではない。

`GroundSurface` はRaycastで地表Yを取得する。主要判定は水平距離だが、全影響を実行比較で否定したわけではない。コアは水平論理位置を基本とし、表示用地表補正をUnity側へ分離する。高さを使う規則が見つかれば地形データと問い合わせインターフェースへ移す。

移行対象はTransform、MonoBehaviour、コルーチン、Time、Resources、ScriptableObject、UnityオブジェクトID、可変static状態。数値型も非Unity型を使う。

- 生成済みBodyBox・射程・攻撃形状・技タイミングをエクスポートする。学習中にモデルやアニメーションを再生しない。
- 初期エクスポートにUnity Editorを使っても、実行・学習には不要とする。
- 座標・射程はワールド単位、移動速度は現行のセル毎秒、時間はシミュレーション秒。`cellSize` を含め単位を明示する。
- 環境ごとにEnergy・デッキ・戦闘登録リスト・時刻を所有する。可変static状態を共有しない。

### 3.2 時間と再現性

- `Step(tickCount)` で進める。`SimulationTickSeconds = 1/60` を初期値案とする。
- 同時処理順は共通コアで一元化。ダメージ・回復解決→生死→占領→所有権→勝敗を基準とし、既存実装との差を検証する。
- Unity版の現行処理順との差は不具合か仕様変更かを記録し、黙って変えない。
- 同点処理は安定したエンティティIDで行い、Unityの生成ID・偶然の列挙順に依存しない。
- 敵判断、手札、待機移動等は用途別乱数ストリームを使い、seedと状態を保存する。
- 初期保証は同一コア版・同一ランタイムでの再現。異なるOS・CPUでのビット単位一致は別途検証する。

## 4. 自動更新するパラメータ

### 4.0 個性・役割・コスト・強弱の割り当て（2026-09-23）

ユーザーの委任に基づく初期案を [キャラ別設計表](rl_character_balance_plan.md) にまとめた。42体それぞれに既存技に沿った個性と弱点を設定し、低コストにも高コストにも「強め」「弱め」を割り当てる。強弱は主にコスト当たりの効率であり、コストによる絶対性能の差をなくす意味ではない。

機械可読の正本は `LearningLab/configs/character_balance_plan.json`。初期案で速度・コストを決め、探索中は固定する。まず8体を単体編成と混成編成で評価する。味方の他キャラと敵基準値を固定し、評価対象だけに候補値を適用する。壁役の攻撃力は固定し、役割に合った探索範囲と目標帯を持たせる。

「強め」「弱め」は設計目標で、測定済みの順位ではない。初回結果は [実験記録](rl_character_balance_first_run.md) を参照。528試合の探索・検証で一部caseの悪化を検出し、探索候補は採用しなかった。ゲームアセットは変更していない。現時点は固定操作による数値最適化であり、操作AIのPPO学習は今回実行しない。

### 4.1 初版のキャラ個別値

強弱の割り当てはユーザーが `LearningLab/configs/strength_assignments.json` で指定する。`weak / standard / strong / conditional` を受け付け、自動探索は割り当てを更新しない。campaignの `--strengths` で別の割り当てファイルも指定できる。

防御力を追加した。計算仕様は [防御力とダメージ計算](defense_damage_spec.md) を参照。**通常攻撃だけに「倍率適用後ダメージ×100÷(100＋防御力)」を適用し、状態異常・状態反応ダメージは防御を無視する。** 既存キャラの初期防御力は0。通常の探索項目 `defense`、またはprofileの `defense_candidates` で探索候補を指定できる。省略時は防御力を固定する。

基準値 `baseline` は実験開始時に凍結する。反復ごとに探索範囲の基準をずらさない。次は共通初期値案であり、キャラ別の明示範囲を優先する。

| 項目 | 実フィールド | 探索範囲初期案 | 単位・制約 |
|---|---|---|---|
| HP | `UnitData.maxHp` | 基準×0.75〜1.25 | 正の整数、刻み1 |
| 防御力 | `UnitData.defense` | 明示した候補のみ（例0/25/50） | 0以上の整数。指定しなければ固定 |
| 攻撃力 | `UnitData.attackPower` | 基準×0.75〜1.25 | 正の整数、刻み1 |
| 移動速度 | `UnitData.moveSpeed` | 基準×0.85〜1.15 | 正値、刻み0.05セル/秒 |
| 出撃Energy | `UnitData.deployCost` | 指定カテゴリ内 | 正の整数、刻み1 |

量子化後にも範囲内の値だけを使い、現行基準値は候補に必ず含める。小さい整数で基準以外の候補がない場合は固定し、自動で範囲を拡大しない。

| 現行CostTier | 許容コスト初期案 | 意図 |
|---|---:|---|
| Low | 1〜3 | 安価な先行・補助・壁 |
| Normal | 3〜5 | 基本編成 |
| High | 5〜7 | 強い単体性能・シナジーの核 |
| Elite | 8〜10 | 高い投資を要する切り札 |

カテゴリの重なりを許容する。役割とカテゴリは同義ではない。探索でカテゴリを変更しない。仮コスト1のままのキャラは完成基準と扱わず、カテゴリと初期コストを先に設定する。

**探索可能なキャラ項目は防御力を含む5項目。初期設定ではHP・攻撃力を更新し、防御力は候補を明示した場合だけ更新する。速度・コスト、攻撃周期と射程は初期運用で固定する。**

### 4.2 第2段階の状態・反応共通値

共通値は同じ状態を使う敵にも影響する。キャラ調整とは別実験にし、変更後に利用者全体を回帰評価する。

| 定義 | フィールド | 初期探索範囲・制約 |
|---|---|---|
| StatusDefinition | `durationSeconds` | 基準×0.8〜1.2、刻み0.1秒、下限0.1秒 |
| StatusDefinition | `damagePerTick` | 正の基準×0.75〜1.25、整数。基準0は固定 |
| StatusReactionDefinition | `reactionDamage` | 正の基準×0.75〜1.25、整数。基準0は固定 |
| 同上 | `durationSeconds` / `durationExtensionSeconds` | 正の基準×0.8〜1.2、刻み0.1秒。基準0は固定 |
| 同上 | `statusDamageMultiplier` / `incomingDamageMultiplier` | 増分(基準−1)×0.8〜1.2を1に加算、刻み0.05、下限1 |
| 同上 | `actionBlockSeconds` | 正の基準×0.8〜1.1、刻み0.1秒。耐性との組み合わせを検査 |
| 同上 | `movementSpeedMultiplier` | 減速量(1−基準)×0.8〜1.2を1から減算、刻み0.05、範囲0〜1 |
| StatusCatalog | `chillMovementMultiplier` | 同上の減速量規則 |
| 同上 | `dazedRecoveryMultiplier` / `lumenDamageMultiplier` | 同上の増分規則 |
| 同上 | `sandedSpreadRadius` | 基準×0.8〜1.2、刻み0.1ワールド単位 |
| 同上 | `sandedSpreadTargets` | 基準±1、整数、下限1 |
| 同上 | `curseDamage` | 正の基準×0.75〜1.25、整数。基準0は固定 |

中立値1や完全停止値0など効果の有無・種類を表す境界は固定する。表と項目別の絶対上下限の共通部分を使い、無効な効果を新設しない。

`damageIntervalSeconds`、`curseCooldownSeconds`、反応の `resistanceSeconds`、寿命方式、成立順、状態消費、位置操作倍率は固定。連続行動不能時間と戦闘時間に占める行動不能率を測り、シナリオ別上限を超える拘束連鎖を不採用にする。

### 4.3 更新しない項目

| 項目 | 理由 |
|---|---|
| `attackTime` / `attackDuration` | CharacterAttackTimingResolverがモーションの発動時刻・全長を優先。UnitDataだけの更新が効くとは限らない |
| 射程・攻撃形状・最大対象数・BodyBox・attackLunge | 技・モデルの生成データと見た目の整合 |
| 移動種別・役割・対象選択・遮蔽無視 | キャラコンセプト |
| 状態ID・反応成立条件・消費規則 | 人間が設計する関係 |
| 付与確率 | 現行StatusCatalog設定1を固定。確率を下げて調整しない |
| ノックバック閾値・位置操作 | 初版の自由度を抑え、制御連鎖は別実験とする |
| 防御力 | 確認したUnitDataに独立したフィールドがない。探索のためだけに新設しない |
| 固有能力・追加攻撃倍率 | 対応データと処理が実装された能力のみ、後日明示登録する |
| AllyDataのdeployCooldown / maxConcurrentSorties | 旧召喚方式と現行出撃制約を混同しない。初版対象外 |
| Energy回復・上限・手札枚数・部隊数 | キャラ調整とシステム調整を分離 |

将来の周期調整は、命中と表示を共通速度設定で整合させるか、攻撃後の追加待機を新設する設計を先に決める。現状の `attackDuration` を単純に自由変数にはしない。

### 4.4 パラメータ定義

必須項目は `parameterId, ownerId, scope, fieldPath, unit, baseline, min, max, step, enabled, dependencyConstraints, sourceVersion`。scopeはキャラ個別/共通を区別する。

探索対象はallowlist方式。未知項目・未実装項目は拒否する。範囲ゼロの固定値は変更量計算から除外する。

## 5. 試験条件

### 5.1 三つのモード

| モード | 条件 | 主目的 |
|---|---|---|
| 単体 | 初期配置固定、Energy回復・再出撃なし | 基本性能と役割 |
| 編成 | 初期予算上限5/10/15/20、配置固定、回復・再出撃なし | 同予算比較とシナジー |
| 実戦 | 初期Energy5、時間回復・手札・再出撃あり | 投入時機・戦力蓄積・攻略 |

予算は使い切らなくてもよい。上限と実支出を保存する。コスト変更で予算超過した必須編成は合法性失敗として扱い、集計から黙って除外しない。

初期時間上限案: `MicroTrialSeconds=60`、`CompositionTrialSeconds=180`、`EpisodeLimitSeconds=600`。有限時間の性能試験と、実戦の勝敗未決着による打ち切りを区別する。

### 5.2 シナリオ群

| ID | テーマ | 主な測定 |
|---|---|---|
| Straight | 直線・標準敵 | 火力、耐久、接敵 |
| LongRoute | 長距離・遠距離敵 | 移動、被弾、到達 |
| Dense | 高密度・低耐久敵 | 範囲、伝播、過剰ダメージ |
| Durable | 少数・高耐久敵 | 単体DPS、DoT、状態維持 |
| Endurance | 継続増援・長期戦 | 前線維持、回復、再出撃費用 |
| MultiFront | 複数経路・複数拠点 | 分散、合流、部隊枠 |

名称だけでは実行可能としない。盤面、敵の種類・数・能力・方策、初期HP、配置・隊列、所持個体、デッキ規則、壁、固定命令、終了条件、seed集合、期待範囲、利用可能機能を必須にする。

### 5.3 評価データの分割

- Tune: 数値探索とRL学習。
- Validation: 候補・チェックポイントの選択。
- Holdout: 採用直前の最終評価のみ。

地形・敵編成・所持構成の変種を分割し、seedだけの変更で汎化したとは判定しない。Holdoutを見て調整した場合、そのケースはValidationへ移し、新しいHoldout版を用意する。

## 6. 評価指標と調整目的

### 6.1 役割別の評価

| 役割 | 主指標 | 補助指標 |
|---|---|---|
| 攻撃役 | 有効ダメージ/試験時間、攻略時間 | 過剰ダメージ、生存 |
| 壁役 | 固定後衛・拠点の損害を抑えた量 | 前線維持、生存 |
| 回復役 | 固定編成の損耗減少 | 実回復、過剰回復 |
| 状態付与役 | 状態対象秒数、相方を含む成績 | 付与・更新・反応回数 |
| 強化・反応役 | 対象効果を無効化した同一編成との差 | 完成前性能、成立時間 |

有効ダメージは残HPまで、実回復は欠損HPまで。戦闘中DPSと試験全時間DPSを分ける。被ダメージ量だけで壁役を評価しない。

共通指標は勝率、未決着率、残メインHP、攻略時間、累計Energy支出、上限で失った回復、再出撃費用、出撃間隔、部隊枠占有、行動不能時間、状態/反応ダメージ、編成分布。

採用率は、手札にあり、単独出撃のEnergy・部隊枠・出撃先条件を満たす判断機会を分母とする。種別と個体札別を分ける。採用率は診断値であり、均等化する目的にしない。

### 6.2 期待範囲と損失

`BalanceTargetProfile` に対象キャラ/編成、役割、得意/通常/苦手条件、基準編成、指標、比較方式、下限、上限、重み、必須制約を定義する。

大きい方が良い値は基準に対する比、小さい方が良い値は逆比など、指標ごとに向きを揃えた値 `x` を定義する。基準または比較値が0で比率が不適切な場合、差分と固定スケールを使う。未決着時の攻略時間は欠測として別に評価し、任意の短い時間へ置き換えない。

```text
deviation(x, lower, upper) = max(lower - x, 0, x - upper)
targetLoss = Σ weight × deviation² / Σ weight
changeLoss = 平均((candidate - baseline) / 許容幅)²
totalLoss = targetLoss + ChangePenaltyWeight × changeLoss
```

`ChangePenaltyWeight=0.05` が初期案。必須制約違反は他の成績で相殺せず候補不採用。目標未指定を全キャラ同値で補完しない。未決着等で必須指標を測定できない場合も自動合格しない。

目標作成の初期案は、同役割・同予算基準に対し通常0.85〜1.15、得意1.10〜1.40。苦手条件と意図した強弱はキャラ別に定義する。全キャラへ自動適用せず、補助専業の火力に攻撃役の下限を課さない。

### 6.3 シナジー

次を併用する。

1. 同予算の代替編成との比較: 選ぶ価値。
2. 同一編成・同一命令・同一seedで対象効果だけ無効化した比較: 効果の寄与。

勝率はpercentage point差、適した非負の性能指標は比率で報告する。単体勝率の合計や異なる単位の加算をしない。分母が小さいときは絶対差を使う。

強度Weak/Medium/Strong/VeryStrongの上昇率初期案は10〜20% / 20〜40% / 40〜70% / 70〜120%。適用指標と対照を指定した試験だけで使い、勝率差へ転用しない。

シナジー定義は必要キャラ集合と重複数、状態、順序、配置条件、無効化する効果ID、期待強度を持つ。3体以上の効果は集合として保存し、ペアの合計へ還元しない。負の相性も登録する。

`DesignedCompositionFraction=0.8` を初期案とし、残りはランダム。種の偏りを抑える探索用と、想定所持分布を使う実戦用を分ける。低コスト大量・重複・別拠点からの合流は明示ケースも設ける。

状態付与元、反応発動者、直接ダメージ所有者を別に記録する。協力者全員に同じダメージを重複加算せず、因果的な寄与は無効化対照で判断する。

## 7. バランス探索

採用案は整数コストの列挙と、範囲を絞ったランダム探索。`IParameterProposer` で方式を交換できる構造とする。全キャラ全項目の同時探索から始めない。

1. 基準・役割・カテゴリ・期待範囲を登録し、結果を凍結。
2. キャラごとにHP・攻撃力を探索。移動速度は移動役割の問題を調べる際に開放。
3. 能力値を固定してコストを列挙。編成可能性・手札停滞も評価。
4. 関連キャラ群をシナジー評価。単体だけで補助役を強化しすぎない。
5. 必要なら共通状態値を別実験で調整し、敵を含む全利用者を回帰評価。
6. 上位案のみ実戦評価。固定方策比較後にRLを適応させ再評価。
7. Validationで選び、Holdoutで最終確認する。

| 設定 | 初期値案 |
|---|---:|
| CandidatesPerBlock | 64 |
| FinalistsPerBlock | 4 |
| ScreeningSeeds | 8 |
| FinalEvaluationSeeds | 32 |

固定した決定的ケースをseed名だけ変えて重複計測しない。比較には共通seed集合を使うが、行動変更により乱数消費順も変わり得る。用途別ストリームやイベント別キーで不要な差を抑える。

試行数と不確実性を併記する。勝率は95% Wilson区間、候補差はシナリオを維持した対応付き再標本化等で確認する。32回で僅差を断定しない。予算内で決まらなければ「未判定」として基準を維持する。

## 8. RL観測

画像ではなく数値・集合・盤面データを使う。schemaを版管理する。

| グループ | 内容 |
|---|---|
| 共通 | 経過時間、Energy、回復進捗、部隊空き枠 |
| 手札 | 札/キャラID、コスト、能力値、状態付与、合法マスク |
| 待機場 | 人間に公開される内容・順序だけ |
| 味方 | 個体/部隊ID、HP、位置、向き、状態、公開される攻撃段階、目的地 |
| 敵 | 公開位置・HP・状態・攻撃動作・出撃予告・経路 |
| 拠点 | 所有者、種別、HP、占有セル、出撃可否 |
| 盤面 | 通行種別、壁と耐久、隣接関係、目的地と到達可否 |

敵内部Energy、未公開の将来判断、乱数状態はactorにもcriticにも渡さない。残クールダウン等が非公開なら、正確な内部値ではなく公開動作・履歴を使う。公開情報一覧を照合し、不明な情報は既定で除外する。

固定スケールで正規化する。可変長の札・ユニット・拠点は集合エンコーダと存在マスクで扱う。容量上限が必要ならシナリオ事前検証を行い、超過はエラー。距離順で黙ってユニットを切り捨てない。

## 9. RL行動と判断時刻

| 操作 | 引数 |
|---|---|
| Wait | なし |
| Deploy | 順序付き手札ID、出撃拠点ID、目的地セル |
| Retarget | 部隊ID、目的地セル |
| Discard | 重複しない手札ID集合 |

Energy使用量は選んだ札から決まる。隊列は選択順。ゲームにない直接増員・瞬間移動を追加しない。

行動は「種別→札/部隊→出撃元→目的地」を条件付きで選ぶ。札を1枚ずつ選び、Stopで終える。選択済みIDと残予算でマスクし、Deployは最低1枚必要。これらはネットワーク内の選択であり、枝ごとに環境時間・報酬を進めない。

PPOでは使った枝の対数確率を合算する。更新時は収集時のマスクを使用し、未使用枝を損失に含めない。目的地は合法セル全体から選び、敵拠点だけへ限定しない。

- `DecisionIntervalSeconds=0.5` を初期案とし、1判断に1命令。その後、対応tick数進める。
- 命令は次tick先頭に反映。途中で勝敗が決まれば即終了。
- Waitは常に合法。無効行動はマスクで除外。
- 古い札ID等の整合違反は環境異常として記録し、黙って有効な操作へ変換しない。
- 建設自動終了・演出省略はシミュレーション時間を消費しない。
- ポーズ・時間倍率・出撃UIのクリック手順は行動に含めない。
- 0.5秒は人間らしさを保証する値ではない。最終候補は判断間隔1秒・2秒でも評価し、高頻度操作依存を別記する。

## 10. 報酬と終了

### 10.1 報酬

初版は疎な終端報酬とし、途中のダメージ・撃破・Energy使用・採用率・多様性には報酬を与えない。

```text
勝利: WinReward + MainHpRewardWeight × clamp(残メインHP / 開始メインHP, 0, 1)
敗北: LossReward
途中: 0
```

初期案は `WinReward=1`、`LossReward=-1`、`MainHpRewardWeight=0.1`。開始HPは正値必須。時間割引で早い勝利を緩やかに選好させるが、勝率・HP・時間の厳密な辞書式最適化ではない。採用判定は勝率を第一にする。

`DiscountPerDecision=0.9995` を0.5秒判断時の初期値とする。判断間隔変更時は `gamma(dt)=gamma(base)^(dt/base)` とし、時間あたりの割引を揃える。

疎報酬で進まなければ、簡単な敵・短い経路のカリキュラムや固定戦術からの初期学習を先に使う。追加の途中報酬は別実験とし、元の攻略指標で改善を確かめる。

### 10.2 終了種別

- `terminated`: 勝敗成立。終端以降の価値は0。
- `truncated`: EpisodeLimitSeconds到達。未決着であり敗北報酬を加えない。最後の観測から価値をbootstrapする。
- `error`: コア・データ・プロセス異常。学習データから分離して報告。

実時間watchdogは処理停止検出専用で、ゲーム内敗北にしない。勝率の分母は有効試行すべて（未決着を含む）。勝利・敗北・未決着・異常件数を併記する。

終了/打ち切りは [Gymnasiumの時間制限仕様](https://gymnasium.farama.org/main/tutorials/handling_time_limits/) に従う。

## 11. 学習方式・初期設定

採用案は **PPO + 条件付き離散行動 + 合法マスク**。公開情報だけでは内部状態が完全に分からないため、方策と価値関数に履歴メモリを持たせる。更新は [PPO原論文](https://arxiv.org/abs/1707.06347) を基準とし、特定ライブラリが複合行動を無改造で扱えるとは仮定しない。

| 名前付き設定 | 初期値案 |
|---|---:|
| ParallelEnvironmentCount | 8 |
| RolloutDecisionsPerEnvironment | 512 |
| LearningRate | 0.0003 |
| PpoClipRange | 0.2 |
| GaeLambda | 0.95 |
| UpdateEpochs | 4 |
| SequenceLength | 32 |
| MinibatchDecisions | 256 |
| EntropyCoefficient | 0.01 |
| ValueLossCoefficient | 0.5 |
| MaxGradientNorm | 0.5 |
| PilotTrainingDecisions | 1,000,000 |
| TrainingSeedCount | 3 |

盤面・キャラ集合・札集合を別に符号化して履歴メモリへ統合する。ネットワーク幅・メモリ次元・パディング規則は実装時に設定化して保存する。上表は出発点であり、必要学習量や性能の保証ではない。

履歴はエピソードでリセットし、系列ミニバッチは境界をまたがない。打ち切りの価値計算にはリセット前の履歴を使う。予算消化を学習成功とは扱わず、曲線と固定戦術比較で判断する。

C# CLIとPythonをプロセス間通信で接続し、Python側にGymnasium形式のadapterを設ける。初版は標準入出力の版付きJSON、ログは標準エラー。step要求をまとめ、速度計測後にバイナリ化を検討する。

Unity ML-AgentsやUnity実行ファイルを学習の必須依存にしない。並列数は実測に合わせる。パッケージ版は実装時の動作確認後にlockする。

## 12. 固定戦術とRL後の再調整

比較方策は合法ランダム、低コスト逐次投入、一定Energyまで温存、壁→火力の順次投入。閾値・目的地規則は設定化する。

1. 基準で固定戦術と複数学習seedを評価。
2. 強い構成・行動列を回帰ケースへ登録。
3. 候補を凍結した同じ方策群で比較。
4. 有望候補では追加学習と新規学習を確認。旧方策の不得意だけを改善と誤認しない。
5. 再学習後のValidationで選び、Holdoutで最終評価。

使われないから弱い、常に貯めるから異常、と即断しない。敵・地形・手札・所持条件を変えても支配的か、意図した弱点が残るかを見る。固定戦術に届かないAIの採用率からキャラの弱さを断定しない。

## 15. 開発順序と受け入れ条件

### M1: 共通コア

- エクスポートしたデータでUnityなしの単体戦闘を完走する。
- 同じ状態・命令・seedで再現できる。
- 移動、隊列、攻撃と中断、状態反応、死亡、占領、Energy、手札を段階的に移す。
- Unity版との比較でイベントtick・対象ID・HP・状態・勝敗を照合する。
- 位置誤差の初期案は `PositionParityTolerance=0.001×cellSize`。
- 現行フレーム依存による差を記録・解決し、一致しない段階で実ゲーム用の候補を採用しない。

### M2: 評価・数値探索

- 6シナリオ群の実データと、代表キャラの役割・基準・期待範囲を登録。
- 単体・編成・実戦の比較とリプレイを出力。
- 初版4項目の候補生成・差分を実装。
- 範囲外・生成層変更・実際には効かない変更を検出。目標未定義の探索開始を拒否。

### M3: プレイAI

- 観測・合法マスク・複合行動・終端/打ち切り・報酬を検証。
- 固定方策比較、複数学習seed、検証ケースを揃える。
- コアstep毎秒、判断毎秒、メモリ、1実験の時間を測り、以後の予算を決める。

### M4: 候補採用

- 必須制約違反、データ欠落、再現不能がない。
- Validationの期待範囲違反が減り、回帰ケースが許容範囲内。
- RL適応後も改善が維持され、Holdoutの勝率・未決着・拠点損耗に説明不能な悪化がない。
- 不確実な僅差は未判定。試行数だけで合格にしない。
- Unityで代表リプレイを表示し、技・移動・隊列の見た目も確認する。

## 16. 実装前に用意する入力と後続拡張

本書の採用案は、Unity非依存共通コア、初版4パラメータ、共通状態値の別段階調整、PPOによる1ステージ攻略。

次は方式選択ではなく、ゲーム固有の入力として作成が必要。

1. 対象キャラID、役割、CostTier、基準値。仮値しかないものは先に初期化。
2. 6シナリオ群の具体的な盤面・敵・所持構成とデータ分割。
3. 得意不得意、基準編成、期待範囲、必須制約、意図して残す強い構成。
4. 公開情報一覧と、矛盾がある現行ルールの採用版。

これらが未設定でもコア・計測の開発は進められるが、自動で適正バランスを決められる状態とは扱わない。

建設学習、ラン全体、獲得方策、敵側RL、攻撃速度調整、Energyシステム自体の探索はM4以降の別拡張とする。
